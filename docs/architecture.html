Flow, architecture, and how it uses LangChain Deep Agents. All data in the project is synthetic.

1. What it does

Delivery platforms (DoorDash, Uber Eats) deduct money from an independent restaurant after a customer reports a missing or wrong item. A chain has a finance team to contest that; an independent owner has a payout CSV and a drawer of order tickets, so they usually absorb it.

Re-Claim reads the payout CSV, finds those refund deductions, ranks them by what is realistically recoverable, gathers evidence from the order tickets and timestamps, drafts a factual and non-accusatory dispute for each strong case, and waits for the owner to approve. Approving prepares a filing packet; the owner files it in the platform's merchant portal (neither platform offers a public dispute API). When the platform answers, the owner records Won or Lost, and the system learns from it.

Three rules shape everything. (1) Nothing is approved without the owner. (2) The agent never states anything it cannot cite to evidence. (3) Money, dates and scores are plain tested code, never the model's guess.

4. How it works, step by step

#StepWhat happens and how
1IngestPlain Python parses the CSV with exact integer cents. Customer names are hashed on load so repeat claimants can be matched without keeping names. Bad rows are reported, never silently dropped. The model never sees the raw file, only a path and counts.
2TriageEach refund deduction is scored: base win rate by claim type, plus fixed adjustments for evidence, plus a small prior from past outcomes. Expected recovery = amount x win probability; earliest deadline breaks ties (14 days DoorDash, about 30 Uber Eats). Each score carries written reasons. Expired cases are zeroed and sink.
3PlanThe orchestrator agent writes a to-do list in queue order and reads the lessons in memory.
4Gather evidenceFor each case the orchestrator hands off to the evidence subagent, which works in a clean context on that one case. It runs three checks (ticket vs claim, pickup timestamps, repeat claimant). Each finding is stored with a source reference. If proof is missing it says so: the case becomes "weak".
5Re-planWhen a case comes back weak, the orchestrator rewrites its plan: demote it, promote the next case, add "request ticket photo". The UI shows the reason on the case and in the agent panel.
6DraftThe dispute-writer subagent drafts a short, factual dispute that cites evidence ids. A deterministic check rejects accusatory wording, unknown evidence ids, drafts that do not name the order, and drafts with no supporting evidence. One retry is allowed.
7ApproveThe agent is paused by interrupt_on on the one tool that files a dispute. The owner approves, edits (edits face the same checks) or skips, in the web app or by text. Only a bare YES approves; "yes, but change it" does nothing. A second check refuses to send anything not approved.
8PacketApproving writes a filing packet and the case shows "Ready to file", with a link to the merchant portal, copy buttons and the deadline. The owner files it.
9LearnThe owner records Won or Lost (or texts WON 28.40 / LOST). The outcome goes to SQLite and a lesson to AGENTS.md. The next run starts from it, and each case explains it: "Starting win rate raised from 55% to 60% because 2 of 3 past missing-item disputes won".

5. How Re-Claim uses LangChain

Re-Claim is built on LangChain Deep Agents (create_deep_agent, on LangGraph) with langchain-anthropic for the model and LangSmith for tracing. Each Deep Agents feature does a job the product needs, not decoration.

FeatureWhereWhy it is used
Subagentsevidence, dispute-writer via the task toolEach case is judged in a clean context holding only that case, so one case cannot contaminate another, and each specialist has a narrow prompt and toolset (5 and 3 tools). The orchestrator's own history is not copied into them.
PlanningTodoListMiddleware (write_todos)The plan is shown live and rewritten when a case turns out weak. This is the visible "re-plan" moment.
Human-in-the-loopinterrupt_on={"send_dispute": ...} + SqliteSaverThe graph pauses at the one irreversible action and resumes only through apply_decision, so approval is enforced by the framework, not by a prompt.
File systemCompositeBackend, FilesystemBackendPer-case notes, drafts, decisions, packets and a local trace live in case folders; the "Agent files" button in the UI shows what the agent actually wrote.
PermissionsFilesystemPermissionThe agent may write only /plan.md and /notes/**. It cannot delete or overwrite audit files, packets or memory.
Persistent memorymemory=["/memory/AGENTS.md"] + recall_similar_casesLessons are loaded into every prompt, so the agent improves with outcomes. The deterministic prior and the agent's lessons point the same way and are both shown to the owner.
TracingLangSmith (opt-in)Every run is a tree: orchestrator, nested subagent calls with their tools, and the approval pause. Tags say whether outputs were replayed or live.

Two LangChain-specific engineering findings

  • Prompt caching was silently off. Deep Agents adds Anthropic prompt caching automatically, but only when the model object is a ChatAnthropic. Re-Claim wraps the model in a record/replay cache, so caching never engaged. We added the cache breakpoints inside the wrapper and measured it on a full live run: 576,337 input tokens, of which 516,572 (89.6%) were cache reads and only 160 were uncached, with 12,106 output tokens.
  • Deterministic offline replay of a non-deterministic agent. The wrapper hashes each request (model, tools, messages) and replays the recorded real-model response. Eight recorded paths replay with the network blocked, and an audit script fails loudly on any miss.

6. Why this design is stronger

This is a comparison of approaches, not a claim that nobody else works on this problem. Recovery services for restaurant chains exist; Re-Claim targets the independent owner who has only a CSV and a drawer of tickets.

QuestionA single-prompt chatbot or a scriptRe-Claim
Who decides what is filed?Often the tool itself, or whoever copies its output.The owner, enforced at the graph level and checked a second time inside the send tool. A bare YES is the only text approval.
Can it invent facts?A prompt can ask it not to.Every claim must cite an evidence id that exists on the case; missing proof makes the case "weak". Accusation wording is rejected by code, including on the owner's own edits.
Who does the maths?The model, with rounding and date errors.Plain code with tests: integer cents, deadlines, scoring with written reasons. The model never assigns a probability.
Does it learn?Rarely; each run starts blank.Outcomes and lessons persist, adjust win rates, and are explained on each case.
Can you audit it?A chat transcript.Per-case folders (evidence, draft, decision, packet, trace), the Agent files viewer, and optional LangSmith traces.
Does it work when the Wi-Fi does not?No.Offline replay of recorded real-model runs, verified with the network blocked.
Is cost controlled?Usually unmeasured.Prompt caching verified (89.6% of input read from cache on a live run), capped output, bounded timeouts, subagents with scoped context.
Is it honest about limits?Varies.The UI says "estimates, not guarantees", labels demo data synthetic, and says that filing is manual.

7. Quality and verification

  • 241 backend tests pass, including 108 edge-case tests: malformed CSVs, expired and same-day deadlines, missing and partial tickets, non-Latin product names, concurrent approvals, a model asking to send several disputes in one turn, two processes writing SQLite, a killed server, a code edit during a run, API timeouts and a missing key.
  • Offline audit: 8 of 8 sample paths replay with the network blocked.
  • Accessibility and mobile: axe-core clean on the main views; no horizontal overflow at 375 px and 414 px widths.

8. Honest limits

  • Text approval is simulated. The parser and bridge are tested; a live Photon link is not built (it needs a Node sidecar and credentials).
  • Re-Claim does not file for you. Neither platform has a public dispute API. It prepares the packet and the owner files it. Recording the result is manual.
  • Win rates are heuristics (a fixed table, evidence adjustments and a small memory prior), not measured platform win rates.
  • Replay covers recorded decision paths. A new CSV needs a live model and API key.
  • Scoring rule, fixed late: a ticket that lists the claimed item no longer raises a missing-item score (it proves the item was ordered, not packed); it still adds points for wrong-item claims, and an omitted item still adds the most. That evidence is also marked neutral, and the draft checker only lets a dispute cite evidence that supports the restaurant. The recorded demo was re-recorded for this, and the model wrapper now makes load_payout run alone in its turn so replays cannot depend on thread timing.
  • Inputs: CSV only; no screenshots, PDFs or Grubhub yet.
